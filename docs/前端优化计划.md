## 1. P0 · 数据加载与缓存（收益最大）

### 1.1 词库/题源文件名带内容指纹 → immutable 缓存

**现状**：`data-N.json` / `quiz-N.json` 走 SW network-first（sw.js:51-52），每次切章至少 1 个 RTT；
弱网下即使内容没变也要等网络往返才能离线回落。worker 对它们发 `no-cache`（worker/index.js:1551-1552），
这是为了"题源改完立刻生效"——正确但代价是每次都要 304 校验。

**改法**：
1. `scripts/convert-data.mjs` 与 `quiz.mjs merge` 产出文件名改为 `data-1.<hash8>.json` / `quiz-1.<hash8>.json`
   （hash 取内容 sha256 前 8 位）；
2. `public/chapters.js` 与 `public/quiz-index.json` 增存文件指纹映射（它们本身保持 `no-cache`，体积小、回源便宜）；
3. worker 对匹配 `-\w{8}\.json$` 的资源发 `cache-control: public, max-age=31536000, immutable`；
4. sw.js 对带指纹的请求走 `cacheFirst`，其余维持现状。
5. app.js 的 `fetchChapterList` / `loadQuiz` 改为从映射取真实文件名。

**收益**：二次访问切章/切认词 **0 网络请求**；22 章词库 + 题源一次访问后永久本地可用。
**风险**：中。引用点散在 e2e / smoke / check / verify-live 脚本里（它们按文件名断言），要全量同步改；
`frontend-guards.test.js` 如断言 fetch 路径也要改。
**门禁**：`npm test` + `npm run check` + `npm run quiz:check` + `npm run e2e` + `npm run smoke`。

**✅ 落地情况（2026-09-30）——改用查询串指纹，不改文件名**：
- 原方案「把 hash 编进文件名」的代价是引用点全量改名（e2e / smoke / verify-live / check 都按文件名断言，
  还会让仓库里躺着 44 个带 hash 的文件、每次改内容都产生一对幽灵文件）。改用**查询串** `data-1.json?v=<hash8>`：
  同一份文件、CDN 与 worker 都认、旧引用点零改动，收益与改文件名完全等价（URL 变 = 缓存键变）。
- 指纹产出：`scripts/quiz-lib.mjs` 新增 `contentHash(text)`（sha256 前 8 位）。
  `convert-data.mjs` 重建时把每章 hash 写进 `chapters.js`（`{ id, name, ..., hash }`）；
  `quiz.mjs` 的 `writeIndex` 从磁盘重算每章 hash 写进 `quiz-index.json` 的顶层 `hashes`。
  两个清单文件自身仍是 `no-cache`（它们是"指纹的载体"，必须先回源）。
- 消费：`app.js` 新增 `chapterHash()` / `quizHash()` / `withVersion(url, hash)`，
  四处取数（`fetchChapterList` 两处、`loadQuiz`、预取）全部包上；**拿不到指纹时回落成裸 URL**
  （绝不能拼出 `?v=undefined` 这种会被永久缓存的键）。
- 服务端：`worker/index.js` 的 `withCachePolicy(res, pathname, url.search)` 增收 search，
  命中 `FINGERPRINTED = /[?&]v=[0-9a-f]{8}/` 就发 `public, max-age=31536000, immutable`。
- SW：`sw.js` 对带指纹请求走 `cacheFirst`（命中即用，连 304 都省），其余维持网络优先保证发版即时。
- 缓存键同步带上指纹：`QUIZ_CACHE_KEY(id, hash)`，避免"同一 spec 下改过题源仍读旧缓存"。
- `frontend-guards` 新增一条守卫：三处 fetch 必带指纹、裸 URL 回落存在、worker/SW 的 immutable 与 cacheFirst 分支存在。
  `npm run e2e` / `smoke` 需 dev 服务与浏览器，本次未跑。

### 1.2 题源纳入本地缓存（当前完全无缓存）

**现状**：`loadQuiz`（app.js:778-800）每次切章都 fetch quiz-N.json（quiz-1.json 279KB，全集约 6MB），
只有内存级缓存，刷新页面即失效；弱网切章白等。

**改法**：复用现有 `idb.js`（已为讲义页配图建好 IndexedDB KV），新增 `quiz-cache` 前缀键，
结构 `{ at, spec, items }`；写入时校验 `doc.spec === QUIZ_SPEC_VERSION`（题源升版自动失效旧缓存），
LRU 无上限（IDB 配额远大于 localStorage）。读路径：先 IDB → 再网络，网络成功后回填。

**收益**：切章/刷新后题源秒开；离线认词全章可用。
**风险**：低。题源 spec 版本字段就是天然的失效开关，不会出现旧题源错配。
**门禁**：`npm test` + `npm run quiz:check`。

**✅ 落地情况（2026-09-29）**：
- 复用 `idb.js`，键 `quiz-cache-N`，结构 `{ at, spec, items }`；读取时 `spec !== QUIZ_SPEC_VERSION` 直接作废。
- `loadQuiz` 改为「先喂 IDB 缓存（立刻可答）→ 网络回来再覆盖」；网络失败但缓存可用时**保留缓存**，
  不再清成"无题源"（原来失败会把 `available` 置 false，离线等于没有题源）。
- `QUIZ_SPEC_VERSION` 在 `public/quiz.js` 新增并导出，`npm run check` 校验它与 `scripts/quiz-lib.mjs` 的值一致
  （前端偏旧 → 旧结构缓存不失效；前端偏新 → 缓存永不命中）。
- 网络仍会回源校验新鲜度（题源改完立刻生效），1.1 的指纹缓存落地后才能真正 0 请求。

### 1.3 词库缓存从 localStorage 迁到 IndexedDB

**现状**：`cacheChapter`（app.js:851-875）用 localStorage 只留 2 章，单章约 80KB；配图为避免 5MB 配额
已迁 IDB，词库还留在 localStorage 挤配额。

**改法**：与 1.2 同一个 IDB 方案，词库键 `chapter-cache-N`，LRU 从 2 提到 22（全章留驻），
保留 `readChapterCache` 的降级语义（IDB 不可用时回落 localStorage 旧逻辑）。

**收益**：离线全词库可用；消除 localStorage 配额竞争；`cacheChapter` 里 try/catch 清配额的兜底代码可删。
**风险**：低。
**门禁**：`npm test` + `npm run check`。

**✅ 落地情况（2026-09-29）**：
- 键 `chapter-cache-N`，LRU 上限 = `CHAPTERS.length`（22，即全章留驻）；淘汰用的"写入时刻"单独存一份小索引
  `chapter-cache-index`，避免为了排序去读 22 份 80KB JSON。
- `cacheChapter`/`readChapterCache` 改为 async（调用点已同步改 await）；IDB 写失败或不可用时回落
  `legacyCacheChapter`（原 localStorage 逻辑，仍只留 2 章）；写入成功后删掉该章的旧 localStorage 键，把配额还给存档。

### 1.4 空闲预取下一章

**现状**：用户按章顺序学习，但切到下一章时才现场加载（loading 卡片 + 最多 3 次重试）。

**改法**：`startRound` 完成后 `requestIdleCallback`（降级 `setTimeout(2000)`）预取
`data-(N+1).json` 与 `quiz-(N+1).json` 写入 1.2/1.3 的 IDB 缓存；
`navigator.connection?.saveData === true` 或 `effectiveType` 为 `2g/slow-2g` 时跳过。
注意预取必须复用 `loadEpoch/quizEpoch` 之外的独立通道（只写缓存，不碰 state），避免与正常加载的
世代守卫打架。

**收益**：顺序学习者切章感知零延迟。
**风险**：低（纯写缓存，不改加载链路）。
**门禁**：`npm test` + `npm run check` + `npm run smoke`。

**✅ 落地情况（2026-09-29）**：
- `startRound` 末尾调 `schedulePrefetch(chapterId)` → `requestIdleCallback`（降级 `setTimeout 2000`）。
- 守三条：① `navigator.connection.saveData === true` 或 `effectiveType` 为 `2g/slow-2g` 时不预取；
  ② 同一章只预取一次（`prefetched` Set）；③ 只写 IDB，**不碰 state**（不参与 `loadEpoch`/`quizEpoch` 世代守卫），
  且缓存里已有就跳过，不重复占带宽。已用 frontend-guards 断言「预取函数体内不得出现 `state.quiz =` / `state.chapter =`」。

## 2. P1 · 首屏与视觉体验

### 2.1 主题首屏闪烁（FOUC）

**现状**：4 个 HTML 均硬编码 `<html data-theme="light">`，主题要等 `ui.js`（模块链末端）执行
`theme.apply()` 才纠正（ui.js:105-133）。暗色用户每次打开先闪一帧亮色。

**改法**：在每个 HTML `<head>` 内联一段 ~10 行非模块脚本（**不用等 module**）：

```html
<script>
  try {
    var t = localStorage.getItem("vocab:theme") || "system";
    var dark = t === "dark" || (t === "system" && matchMedia("(prefers-color-scheme: dark)").matches);
    document.documentElement.dataset.theme = dark ? "dark" : "light";
  } catch (e) {}
</script>
```

注意 `theme.stored()` 的实际存储格式以 ui.js:94-105 为准，内联脚本与其保持同一解析逻辑；
`theme-color` meta 也同步切（ui.js:113 已有同样逻辑可抄）。

**收益**：暗色用户首屏零闪烁。
**风险**：低，但 4 个 HTML 都要改，`ui:baseline` 截图基线需重录。
**门禁**：`npm run check` + `npm run smoke`。

**✅ 落地情况（2026-09-29）**：
- 4 个 HTML 的 `<head>` 各加一段内联引导脚本（放在 `theme-color` meta 之后、样式表之前）。
- **踩坑**：worker 的 CSP 是 `script-src 'self'`，内联脚本会被拦。解法不是放宽 `unsafe-inline`，
  而是给这段固定文本登记 CSP **哈希源**（`worker/index.js` 的 `THEME_BOOT_SHA256`，
  当前值 `5DfasPoytUowgxWp02sUgI5ot522id3jAtFczTQWz5w=`）。
- `npm run check` 新增两条守卫：① 四页脚本内容一致且哈希与 worker 登记值相同；
  ② 存储键 `vocab:theme` 与双主题 `theme-color` 取值和 `ui.js` 一致。改脚本忘了改哈希会直接判失败。

### 2.2 计时器漂移

**现状**：限时作答用 `setInterval`（app.js:3988）倒数。页面切后台时浏览器把 interval 节流到
1 秒+，回前台显示的时间已经落后真实流逝时间——限时模式在切后台后"偷时间"。

**改法**：改为「目标时间戳」制：开始时记 `deadline = Date.now() + limitMs`，interval（或 rAF）
每次tick只做 `remain = deadline - Date.now()`，显示与判负都以 remain 为准。
这样后台节流、系统休眠都不影响判定。

**收益**：计时严格准确，消除"切后台多拿时间"的公平性漏洞。
**风险**：低。注意判负时机从 interval 回调改为 remain<=0 检查，保持现有 `state.timedOut` 语义。
**门禁**：`npm test` + `npm run check` + `npm run smoke`。

**✅ 落地情况（2026-09-29）——前提有误，实际改动不同**：
- 现状**早已是 deadline 制**（`startTimer` 存 `performance.now() + 秒数`，`tickTimer` 用
  `deadline - performance.now()` 判负），app.js:3988 那个 `setInterval` 是账号 UI 的 120s 心跳，与倒计时无关。
  因此"倒计时漂移"并不存在，本条**无需重写计时**。
- 但顺着读发现一个真实缺陷：`state.timer.hiddenAt` 会跨题残留。场景——隐藏页面时开启/关闭过限时
  （`bindTimerVisibility` 在 `timerEnabled=false` 时直接 return，`hiddenAt` 不复位），
  下次切回前台会执行 `deadline += now - hiddenAt`，把整段间隔补偿给用户，**限时形同虚设**。
- 修法：`startTimer()` / `stopTimer()` 均复位 `hiddenAt`；`bindTimerVisibility` 在限时关闭时也复位。
  切后台"停表补偿"的设计意图保持不变（不因切走而判错）。
- 补了 `frontend-guards` 回归用例：禁止退回递减计数、禁止 hiddenAt 残留。

### 2.3 backdrop-filter 降级策略

**现状**：5 处毛玻璃（topbar、弹层、toast、quick-menu、遮罩）。topbar 常驻 blur 面积小可接受；
ui.css:755 的 `blur(6px)` 遮罩和大面积弹层在中低端 Android 上是掉帧大户。

**改法**：
1. 确认 5 处各自作用对象（app.css:449/485、ui.css:290/650/755），大面积遮罩（>50% 视口）降级为
   纯色半透明；
2. 在 tokens.css 的 `prefers-reduced-motion: reduce` 媒体查询里统一 `backdrop-filter: none`，
   与动效降级同开关；
3. （可选）`@supports not (backdrop-filter: blur(1px))` 的纯色回落确认已存在，没有则补。

**收益**：低端机滚动/开弹层帧率明显改善。
**风险**：低，纯视觉。`ui:baseline` 需重录。
**门禁**：`npm run check`（设计 lint 会查）+ `npm run smoke`。

**✅ 落地情况（2026-09-29）**：
- `.scrim`（ui.css）是唯一一块"整屏合成"的模糊 → 直接去掉 `backdrop-filter`，底色由 0.5 提到 0.62 保证弹层可读。
- tokens.css：`prefers-reduced-motion: reduce` 里统一 `backdrop-filter: none`，**并把 `--glass`/`--glass-strong`
  换成新增的不透明变量 `--glass-opaque`/`--glass-strong-opaque`**——否则关掉模糊后半透明底会透出底层文字。
- 补 `@supports not (backdrop-filter)` 的同一套不透明回落（老 Safari/WebView 原本没有）。
- 设计 lint 新增 8e：`.scrim` 不得再出现 `backdrop-filter`、降级与 `@supports` 回落必须存在、不透明变量双主题都要定义。

### 2.4 弹层焦点管理

**现状**：`openAppSheet`（app.js:195-231）动态建弹层，未见焦点圈定与焦点还原；键盘/读屏用户
焦点会留在弹层背后的页面上。

**改法**：打开时记录 `document.activeElement`，焦点移入弹层第一个可交互元素；
`Tab`/`Shift+Tab` 在弹层内循环（focus trap）；`Esc` 关闭；关闭后焦点还原到触发元素。
quick-menu（index.html:180）同理。

**收益**：键盘与读屏可用性达标（`npm run a11y` 可补充用例）。
**风险**：低。
**门禁**：`npm test` + `npm run a11y` + `npm run smoke`。

**✅ 落地情况（2026-09-29）——弹层本就达标，缺口只在 quick-menu**：
- `openAppSheet` 只是 `openSheet` 的包装，`ui.js` 的 `openLayer` 已实现「记录旧焦点 → 关闭还原 + Esc + Tab 循环」，
  所以弹层侧无需改动（本条写作时误判）。
- 真正缺的是 index.html 的「更多操作」浮层（`quickMenu`）：原来只切 `hidden`，键盘用户打开后焦点仍留在
  触发按钮上、Tab 会走到浮层背后的答题控件。已补齐：打开即聚焦首个可交互元素、Esc 关闭并还原焦点、
  Tab/Shift+Tab 在「触发按钮 + 菜单项」间循环、点外部关闭时若焦点在菜单内也还原。
- `npm run a11y` 需要 axe-core（未安装，`npm i --no-save axe-core`），本次未跑；改用 `frontend-guards`
  源码守卫锁定上述行为。

## 3. P1 · 同步可靠性

### 3.1 关页最后一答改用 sendBeacon / keepalive

**现状**：`visibilitychange` 时会 flush（app.js:1954/3787），但 `beforeunload`/`pagehide` 瞬间
发起的 `fetch` 可能被浏览器中止——"答完最后一题立刻关页"存在丢更新的尾巴。

**改法**：`pagehide` 时用 `navigator.sendBeacon(url, blob)` 发最后一批脏数据（Content-Type
`text/plain`，body 仍是 JSON 字符串，worker 端按 JSON 解析即可，无需改协议）；不支持 beacon 的
环境回落 `fetch(..., { keepalive: true })`。注意 beacon 单包上限 64KB，超过时只发前 N 条并保留脏集合。

**收益**：最后一答不再丢。
**风险**：中低。worker 需接受 beacon 的 Content-Type；e2e 要补 beacon 通道用例。
**门禁**：`npm test` + `npm run e2e`。

**✅ 落地情况（2026-09-29）——改用 keepalive fetch，不是 sendBeacon**：
- **关键前提**：`sendBeacon` **无法携带 `Authorization` 头**，而本项目是 Bearer token 鉴权，
  无头请求会被 401 拒掉。故选 `fetch(..., { keepalive: true })`：同样由浏览器接管、页面销毁后仍能发完，
  且能带自定义头。worker 端协议零改动（就是普通 `PUT /api/vocab/words`）。
- 新增 `Auth.pushWordsKeepalive(changes)`（vocab-auth.js）与 `flushOnLeave()`（app.js）：
  挂到 `pagehide` + `beforeunload`（后者在 iOS Safari 常不触发，故两者都挂，用 `leaveFlushSent` 去重）。
- **不清脏集合**：keepalive 读不到响应，成败未知；脏集合原样保留，下次进页面由 `markAllDirty` 重发兜底。
  单包按 58KB 截断，超出的留待重发。
- 现状核对：原 `visibilitychange` 只 `saveLocal()` + 拉云端（不推送），最后一答若撞上 800ms 防抖窗口就丢——
  该尾巴已由本条补上。`npm run e2e` 需 dev 服务，本次未跑。

## 4. P2 · 渲染细节

### 4.1 renderOptions 对齐 renderSlots 的增量模式

**现状**：`renderOptions`（app.js:1461-1504）每次全量 `replaceChildren()` 重建 4 个按钮；
`renderSlots` 已示范了"节点缓存 + 只改 class/text"的更优模式（app.js:1602 注释即为此而写）。

**改法**：选项节点按 index 缓存于 `state.dom.optionNodes`，题目不变（如答题态切换、上一题回看）
时只更新 class / textContent / aria 属性；换题才重建。

**收益**：单次成本本来就小（4 节点），收益主要是消除答题瞬间的布局抖动与屏幕阅读器重复播报。
优先级因此定 P2。
**风险**：低，但要保证 `dataset.index` 与选项重排（错题复现 `key#rN` 换序）后的一致性。
**门禁**：`npm test` + `npm run check`。

**✅ 落地情况（2026-09-30）**：
- `state.dom.optionNodes`（节点数组）+ `state.dom.optionsFor`（当前题目对象）做缓存判据；
  题目对象变了或选项个数变了才重建，否则只改 class / textContent / aria。
- 每个节点上写 `dataset.sig`（内容签名），只在签名变化时才重写内部 HTML——比只比"是不是同一题"更细，
  错题复现 `key#rN` 换序时能正确更新而不错位。
- 守卫：断言同题重渲染不得出现 `replaceChildren()` 后整块重建的写法（会让读屏重复播报四个选项）。

### 4.2 renderSlots 同长度换词无入场动画（确认是否有意）

**现状**：`renderSlots` 只在 `childElementCount` 变化时重建节点并播 `enter` 动画
（app.js:1608-1628）。相邻两词字母数相同时复用旧节点 → 无入场动效。若是有意为之（减少闪烁）
则保持；若是疏漏，在换词时对复用节点重放一次 `enter`。

**改法**：先确认设计意图，再决定是否补一行重放逻辑。
**风险**：无（仅确认）。
**门禁**：`npm run check`。

**✅ 落地情况（2026-09-30）——属疏漏，已补**：
- 判定从"槽位数变了"改为"`rebuilt || state.dom.slotsFor !== wordKey`"，等长换词也会重放入场动效。
- 连续换词时上一个词的收尾定时器会把新词的 `enter` 提前摘掉，故重放前先 `clearTimeout(slotEnterTimer)`；
  重放靠 `void host.offsetWidth` 强制回流再挂 class，否则同一帧内增删 class 浏览器会合并、动画不播。

## 5. P2 · 发布与工程化

### 5.1 sw.js VERSION 自动化

**现状**：硬约束第 10 条靠人肉记"改静态资源递增 VERSION"（sw.js:14），属于易漏项。

**改法**：二选一——
- （轻）`scripts/check.mjs` 增加检查：`git diff --name-only HEAD~1 -- public/` 有变更且
  sw.js 无变更时告警（不阻断，warning 级）；
- （重）构建脚本把 `git rev-parse --short HEAD` 注入 sw.js 的 VERSION，彻底免人肉。

**收益**：消除"老用户拿不到更新"事故类。
**风险**：低（轻量方案）/ 中（注入方案要处理 wrangler dev 的本地路径）。
**门禁**：`npm run check`。

**✅ 落地情况（2026-09-29）——选了轻量方案**：
- `scripts/check.mjs` 新增第 9 节：用 `git status --porcelain -- public/` + `git diff --name-only HEAD~1`
  （工作区与上一个提交都看，本地开发到一半和 CI 事后复查都覆盖），
  发现 `public/*.html|js|css` 有改动而 `sw.js` 没动 → 打印 `⚠` 提醒（warning 级，不阻断）。
- `data-N.json`/`quiz-N.json` 不计入（网络优先 + 按章请求的内容数据，不需要靠 VERSION 失效）。
- 不在 git 仓库或无 git 时自动跳过。顺带把本次改动对应的 `VERSION` 由 `v6` 递增到 `v7`。

### 5.2 引入 esbuild 构建（压缩 + 指纹）

**现状**：JS/CSS 原样上线，app.js 144KB、lecture.js 84KB 未压缩；无指纹导致 1.1 的
immutable 缓存无从谈起。

**改法**：加 `npm run build:assets`：esbuild 压缩 `public/*.js|css` 到 `public/dist/`，
文件名带内容指纹，HTML 引用随之改写（小脚本处理）。wrangler 静态目录指向不变。
压缩后 app.js gzip 前约省 35-40%，gzip 后约省 25-30%。

**收益**：首屏与切页传输量下降；与 1.1 的指纹缓存形成闭环。
**风险**：中。smoke 测试的 105 项直接跑在 public 文件上，要同步指向 dist；
sourcemap 要保留（排障依赖）。
**门禁**：全套（`npm test` + `check` + `e2e` + `smoke` + `verify:live`）。

**✅ 落地情况（2026-09-30）**：
- `scripts/build-assets.mjs`（`npm run build:assets`）：esbuild 打包 4 个页面入口（`bundle` + `splitting`），
  产物进 `public/dist/`，文件名 `[name].[hash]`（esbuild 的 hash 是大写 base32，
  与 `contentHash()` 的 8 位十六进制不同，所以 worker/SW 的识别正则写成两条）。
  实测：app.js 141→77KB（-45%）、lecture.js 77→36KB（-54%），另产出 6 个跨页共享 chunk。
- **源码留在原地**不删：`test/frontend-guards.test.js` 按正则断言 app.js 源码、`scripts/check.mjs`
  也要读源码做静态校验，源码必须是可读原始文件。产物只是"上线形态"。
- **CSS 逐文件 minify 不合并**：它们之间没有 `@import`，保持多个小文件才能让 tokens/ui 跨页命中同一份缓存；
  合成 per-page 大文件反而每页各缓存一份重复内容。
- HTML 改写**幂等**：先把 `dist/x.<hash>.js` 还原成 `x.js` 再按新产物重写，否则第二次构建会拼出
  `dist/dist/x.<hash>.<hash>.js`。只改 `href`/`src` 的值，不误伤正文。
- **防漏构建**：`npm run dev` 挂 `predev`、`npm run deploy` 显式串 `build:assets`；
  `check` 新增第 10 节比对 manifest 里的源码指纹，源码改了没重建会告警（warning 级）。
  `public/dist/` 已被 `.gitignore` 的 `dist/` 规则覆盖，不入库。
- **踩坑**：① SW 的 `ADMIN_PATH` 原本是 `/^\/admin\.(html|js|css)$/`，后台脚本变成
  `dist/admin.<hash>.js` 后不再匹配 → 后台产物会落进 PWA 离线缓存，已改成同时匹配两种形态；
  ② smoke 里 `page.route("**/data-*.json")` 匹配不上带查询串的 `data-1.json?v=<hash8>`，
  glob 换成正则 `/\/data-\d+\.json/`，否则"抖动/断网"用例**根本拦不到、会假绿**；
  ③ SW 缓存命中判断 `caches.match("/data-1.json")` 要加 `{ ignoreSearch: true }`。
- `npm run e2e` 增一条：首页引用的 dist 产物必须带 `immutable`（实测 `public, max-age=31536000, immutable`）。

### 5.3 JSON 构建期 minify

**现状**：`data-N.json` / `quiz-N.json` 为带缩进文本（quiz-1.json 279KB，minify 后约 -15~20%）。
CF 会自动 gzip/br，收益被压缩抵消一部分，但解析期内存与离线缓存体积仍实打实受益。

**改法**：`convert-data.mjs` / `quiz.mjs merge` 产出时 `JSON.stringify` 不带缩进；
仓库里如需可读性，保留 `content/quiz/` 的 pretty 中间分片作溯源（现状正好如此，无需新增）。

**收益**：传输与 IDB 缓存体积下降。
**风险**：低。注意 `quiz:check` 与扫描脚本读法兼容（`JSON.parse` 不受影响）。
**门禁**：`npm run quiz:check` + `npm run check`。

**✅ 落地情况（2026-09-30）**：`convert-data.mjs` / `quiz.mjs` / `fix-truncated-why.mjs` 的写盘处统一改成
`JSON.stringify`（不带缩进），22 份题源合计 4.35MB → 2.74MB（**省 37.1%**）。
`check` 新增守卫：data/quiz JSON 里不得再出现缩进（`/\n\s/`），防止有人手工编辑后把体积又带回来。

### 6.1 app.js 拆分（4005 行 → 模块群）

**门禁**：每 PR `npm test` + `npm run check` + `npm run smoke` 全绿。

**✅ 落地情况（2026-09-30，第一轮：拆出 3 个模块，app.js 4068 → 3800 行左右）**：
