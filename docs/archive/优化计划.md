**浏览器端到端发现并修掉的 3 个真实缺陷**（单测与静态检查都没覆盖到）：

1. 设置面板里那颗按钮写着「登录 / 注册」，但打开的表单固定是**登录**，直接提交会打到 `/api/auth/login` 得 401 —— 已改为顶部明确的「登录 / 注册」分段切换。
2. 清空本机存档（或换设备）后重新登录，**只恢复了数据、没有恢复到上次的章节** —— 现在云端 `resume.chapter` 会在"本机无进度且无深链指定章节"时生效。
3. **【线上可见】用 `hidden` 属性隐藏的状态卡片一直显示在页面上**：组件里的 `.stack{display:flex}` / `.loading-card{display:flex}` / `.chip{display:inline-flex}` 覆盖了浏览器默认的 `[hidden]{display:none}`，导致「正在加载词库…」和「词库加载失败」以及计时/复习横幅常驻页面。已加全局 `[hidden]{display:none!important}`，并把冒烟断言从"查 hidden 属性"改成"查真实可见性"。

**本次一并做的可用性加固**（针对线上网络抖动）：

- 词库请求失败**自动重试 3 次**（重试时绕过缓存），只在彻底失败后才报错；
- 报错改成**人话**：`网络连接中断（已自动重试 3 次）`，而不是把 `Failed to fetch` 甩给用户；
- **本机缓存兜底**：成功加载过的章节写入 localStorage（最多留 2 章），彻底取不到时用它继续，并提示"正在使用本机缓存的词库"；
- 出错时**保留章节按钮**，用户可以直接换章节，不会卡在错误页；
- 把「💡 提示字母」控件**放回主界面**（旧版位置），设置抽屉里同一项保留并双向同步。

## 0. 结论摘要

**做得好的部分**

- 拼写引擎本身完整且正确：随机/看中文/听音三种模式、提示档位、计时、错题本与生词本、章节切分、语音朗读、音效、深色模式、回车提交，桌面端主流程是通的。
- 云端账号体系（PBKDF2 100k + 30 天会话 + D1 存储 + cron 清会话）结构清晰，`worker/index.ts` 只有 198 行，边界处理（404 不穿透静态资源、body 大小限制、JSON 解析容错）做得比一般个人项目扎实。
- 讲义页的 pointer events、coalesced events 批注、键盘左右键翻词，是比刷词页更成熟的交互实现。

**三个必须优先解决的问题**

1. **手机端完全无法使用（P0）** —— 刷词页没有任何文本输入元素，字母输入只依赖 `document` 上的 `keydown`（`index.html:1561-1586`），全页唯一的 `<input>` 是侧边栏搜索框（`index.html:959`）。触屏设备没有物理键盘，虚拟键盘不会弹出 → 用户只能「跳过」。但页面写了完整的移动端布局（`index.html:906-938`，「讲义」页还有触控笔批注）→ 说明原本就是要支持手机的，只是输入这一环没实现。
2. **云端同步会丢数据（P0）** —— 新设备/清缓存后登录，本地无存档时 `loadState()` 直接 `return false`（`index.html:1204`），走 `switchChapter(1).then(resetAndStart)`（`1661-1665`），而 `resetAndStart()` 会清空该章两本书并立刻 `saveState()` 上云（`1328-1339`）→ **云端第一章进度被空数据覆盖，其余章节也不会被拉取**。另外 `VocabAuth.onLogin` 从未被注册（`vocab-auth.js:196` / `index.html` 无调用），登录成功后不会触发云端合并。
3. **误触即永久删除（P0）** —— 「🔄 重新开始」紧邻主按钮（`index.html:1022-1028`），移动端两者还在同一 2 列网格里上下相邻（`923-929`）；点击后无任何确认即清空该章错题本+生词本并立即写入云端（`1590` → `1328-1339`）。「清空」两个按钮同样无确认（`1592-1593`）。

**一句话判断**：桌面端是一个"能用的练习器"，移动端是"能看不能用"，而学习闭环（错词复现、掌握判定、进度语义）还没有成立 —— UI 打磨之前，这三件事的价值远大于配色和圆角。

## 5. 需要先定的 3 个决策

1. **移动端是不是一等公民？** 若是，Phase 0-1 与 Phase 2-7 必须优先；若目标是桌面/平板+笔，则 0-1 可降级为「提示请使用电脑」，但讲义页的触控批注暗示并非如此。
2. **后端改到「按词存储」（Phase 3-1）是否现在就做？** 它是多端同步、SRS、章节统计三件事的共同前提。若只在一台设备上用，可以先跳过，把 Phase 1 的错词复现只做本地版。
3. **是否接受一次性的数据格式迁移？** Phase 3-4（`.js` → `.json`）和 3-1（blob → 按词）都涉及线上数据；建议在 Phase 0 就加上「导出/导入 JSON」按钮作为兜底。

# 第二期：认词模式（看英文选中文）

> 状态：**功能与架构已完成并上线**；题源已产出 5 章（6 / 7 / 8 / 10 / 17，见 `public/quiz-index.json`），其余章节按生成规范分批补齐。

## 9. 需求与判断

- 需求原话：*"不是所有的英文都需要拼写，更多的是要认识，可以做成选择题"*。
- 需求追加（2026-09-20）：*"选择题除了看英文选中文，还要看中文选英文"* —— 反向认词立项为**第三期**，见文末。
- 判断：一个词库里真正需要"会写"的只是少数，多数词只要**看到能认出来**。
  所以这不是给拼写加个开关，而是**第二种答法**。
- 结论：**两种答法（拼写 / 认词）共用一个词状态与同步协议**，出题规则单独成模块。

## 10. 架构（这一期做了什么）

| 层 | 落点 | 说明 |
|---|---|---|
| 出题逻辑 | `public/quiz.js`（新，纯函数） | 干扰项挑选、辨析文案、位置打乱、反作弊；可注入 rng，全部可单测 |
| 题源 | `public/quiz-N.json` + `public/quiz-index.json` | 精编干扰项与辨析；清单决定前端要不要请求（无题源零多余请求、无 404） |
| 交互 | `public/app.js` | 练习方式分段控件、选项区、辨析卡片、键盘 1-4/A-D、答对自动下一题 |
| 样式 | `public/app.css` | `.option` / `.quiz-note` / `.prompt-word`，桌面 2×2、移动单列 |
| 设置 | `public/core.js` | `answer` / `quizPrompt` / `autoNext` 三个设置项（随云端同步） |
| 分模式成绩 | `core.js` 台账 `modes` | 只存本机：避免"只做过选择题"的词在拼写模式里被当成已掌握 |
| 工具链 | `scripts/quiz.mjs` + `scripts/quiz-lib.mjs`（新） | `prompt`（给模型出题）/ `check`（校验）/ `sample`（抽查）/ `merge`（合并）/ `index` |
| 生成规范 | `docs/选择题资料生成规范.md`（新） | 干扰项六类与配额、辨析写法、红线、正反例、提示词区段、验收标准 |

**关键设计取舍**

1. **掌握状态不分模式**：同步协议仍是"按词 LWW + 一份 s/cs/wc/seen/due"。
   分模式细节放本机台账，`masteredForPractice()` 保证"只认过没拼过"的词在拼写模式里仍要练。
   代价是多设备不同步这部分统计（可接受，记录在 README 已知限制里）。
2. **题源缺失不影响可用**：`quiz-index.json` 里没有的章节，前端一次请求都不发，
   用同章词按分数自动挑干扰项（同词根 > 差一个字母 > 形近 > 近义 > 词性 > 同主题），
   并保证"不会出现两个都说得通的选项"。精编题源的价值是补上**语义**判断。
3. **`need: "read"`**：只认不拼的词不进拼写牌堆（选择题照常出现），给"只求读懂"的词一条路径。
4. **选项位置稳定**：用 `chapter:word` 当随机种子 → 同一题每次进入选项位置一致，回插/重渲染都不跳位。

## 11. 这一期明确不做

- 不生成具体题源内容（用户明确说"具体的选择题资源暂时不要做"）——只交付功能、架构与生成规范。
- 不做反向题（看中文选英文）—— 经用户确认已立项为**第三期**（见文末）；拼写填空、句子选词仍不做，`promptKind` 已预留扩展位。
- 不把分模式台账上云（要上云就得改 D1 表与同步协议，收益不匹配）。

# 第三期：认词反方向（看中文选英文）

> 状态：**计划中（未开始）**。由 2026-09-20 追加需求立项：*"选择题除了看英文选中文，还要看中文选英文"*。

## 13. 需求与判断

- 需求原话：*"选择题除了看英文选中文，还要看中文选英文"*。
- 判断：正向题（看英文 → 在 4 个中文释义里挑对的）考的是"见到这个词知不知道意思"；
  反向题（看中文释义 → 在 4 个英文词里挑对的）考的是"想表达这个意思时能不能把词认领回来"，
  恰好是「认词」与「拼写（看中文写单词）」之间的天然中间档 —— 认得出 ≠ 写得出，但反向认得出说明已经接近。
- 结论：**不新增第三种练习方式**。反向只是认词模式里的一道新题面方向：
  出题入口、词状态、同步协议、键盘 1-4/A-D、答对自动下一题全部复用，只把"题面 / 答案 / 选项"掉个头。

## 14. 方案（要做哪些改动）

**方向挂在现有 `quizPrompt` 设置上，不新增第二套开关**：认词的"出题方式"分段控件从
`看英文 / 听音 / 随机`（`app.js:2209` `QUIZ_MODES`）扩为 `看英文 / 看中文 / 听音 / 随机`；
「随机」档本就每题重抽（`app.js:827` `pickPromptKind`），天然实现三向混合。

| 层 | 落点 | 改动 |
|---|---|---|
| 出题逻辑 | `public/quiz.js` | `buildChoiceQuestion()`（`quiz.js:386`）增方向：反向时 `answer = word`、题面 = `meaningCN(+pos)`、选项 text = 英文词。`questionKey()`（`quiz.js:370`）改为 `${chapter}:${wordId}:${dir}`，选项位置种子（`quiz.js:418`）随之带上方向 —— 同一词正/反两向各自位置稳定，互不串位。`explainChoice()`（`quiz.js:457`）文案按方向取词（正向"正确释义是"，反向"正确答案是"） |
| 干扰项 | `public/quiz.js` | 判定规则原样复用：`isUsableDistractor`（`quiz.js:193`）的"释义互含即排除"在反向同样成立（干扰项词条的释义与题面互含 → 那个英文词也说"对"，必须排除）；`classifyDistractor`（`quiz.js:211`）本就按英文词形/词根/释义重合打分，反向时这些维度反而更对症。仅 `pickDistractors` 返回的选项 text 由 `meaningCN` 换成 `word`（`quiz.js:345` 已带 `word` 字段，改动很小） |
| 题源 | `public/quiz-N.json` | schema 升 **1.1**：item 增可选 `"rev": { "distractors": [{ "text": "reveal", "kind": "form", "why": "…" }] }`（text = 英文词）；正向字段一字不动，旧题源完全兼容。无 `rev` 的词反向题走同章词自动兜底 —— 与正向同一条硬规则：**题源缺失不影响可用** |
| 校验/工具 | `scripts/quiz-lib.mjs`、`scripts/quiz.mjs` | `validateQuizDoc()`（`quiz-lib.mjs:149`）增 rev 侧规则：text 为纯拉丁词、不得等于答案词或其屈折变形、干扰项的中文释义（词库内可查；词库外的词必须带 `gloss` 字段）不得与题面互含、kind/why 与正向同标；`prompt` 命令（`quiz.mjs:374`）增反向出题提示词区段，`check/sample/merge/index` 原样透传 |
| 交互 | `public/app.js` | `QUIZ_MODES`（`app.js:2209`）加 `["zh", "看中文"]`；`pickPromptKind()`（`app.js:827`）认词题面池加 `"zh"`；`ensureQuestion()`（`app.js:842`）缓存 key 带方向；`renderWord` 播报（`app.js:905`）与题干渲染（`app.js:1017-1032`）加 zh 分支：大字显示中文释义，英文词与音标照旧"答完再揭示"；`renderOptions()`（`app.js:1101`）反向选项渲染英文词（音标作小字）；🔊 播放在反向题面改为答对后朗读英文（听音强化，不泄露答案） |
| 设置 | `public/core.js` | `quizPrompt` 白名单（`core.js:376`）加 `"zh"`；向前兼容由现有 `includes` 检查天然兜住（旧版本读到 `"zh"` 回落 `"en"`，不会崩）。云端同步协议不变（仍是同一字段，只是值域扩大） |
| 样式 | `public/app.css` | `.option` 增英文词样式（等宽字号、词长差异大时不换行折断），反向题面复用 `promptCn` 现成结构 |

**不需要动的**：拼写模式全套、错题/生词回流、按词同步协议、分模式台账（方向不进台账，
与第二期"分模式统计只存本机"同级取舍，记入 README 已知限制即可）。

## 15. 内容节奏（题源）

- 反向精编题源与正向**同一批生成**：同一个词、同一个模型上下文里正反各出一组干扰项，
  边际成本远低于单独跑一轮；生成顺序沿用第二期结论（第 21 章 → 第 1 章 → 已覆盖 5 章补 `rev` → 其余按章推进）。
- `docs/选择题资料生成规范.md` 升 v1.1，新增"反向题（看中文选英文）"一章：
  六类干扰项在反向下的映射（同词根/形近在反向里杀伤力最大；近义在反向里直接踩"两个选项都对"的红线）、
  红线（干扰项释义与题面互含即废、答案不得永远最长）、正反例、提示词区段。
- **功能上线当天反向题即可用**（同章词自动兜底先行），精编 `rev` 随内容批次逐章覆盖 —— 不互相阻塞。

## 17. 需要先定的 2 个决策

1. **认词「随机」档默认是否扩为三向混合（看英文/看中文/听音）？**
   建议：是 —— 反向从第一天起就有自动兜底可用，且需求本就是"两个方向都要"；
   只想练某一向的用户在分段控件里锁定单档即可。
2. **反向干扰项是否允许词库外的英文词？**
   建议：允许（与正向允许词库外中文释义对齐），但必须带 `gloss`（一句中文释义）供
   "两个都说得通"校验与辨析兜底；只允许同章词是更保守的替代，但形近词（repeal/reveal）往往不在同章，质量会打折。

**工作量估算**：功能与架构 1～1.5 天（quiz.js + app.js + core.js + 样式 + 测试 + 校验器）；
题源内容随正向批次滚动生成，不单独排期。
